## Executive summary

A new Airbnb host has no booking history, so they have no data-driven way to
price their first night. This project builds a model that predicts a
defensible starting nightly price from listing attributes alone — location,
room type, capacity, amenities — trained on 7,000 Melbourne listings and
validated on a further 3,000. The best model (Histogram Gradient Boosting on
a log1p-transformed price) predicts within **A$72.89** of the true price on
average, and within **A$50.20** once the top 1% of ultra-premium listings are
excluded. The approach placed **3rd of 20** in a cohort-wide Kaggle
competition.

<Insight title="Key takeaway">
  Location and room type dominate price — see the exploratory charts below — but
  they only explain part of the story: the model accounts for roughly a quarter
  of price variance (R² = 0.248), which is realistic for a market this noisy and
  should be communicated to hosts as a *starting anchor*, not a guaranteed rate.
</Insight>

## Business problem

Hosts price a new listing by guessing, copying a neighbour, or under-pricing
to win early reviews — all of which cost money in the first few months. The
decision this model informs: **what nightly price should Airbnb (or a host
onboarding tool) suggest before any booking history exists?** Getting this
wrong in either direction has a cost — too high and the listing sits empty,
too low and the host leaves money on the table for months.

## Data overview

|          | Train | Test  |
| -------- | ----- | ----- |
| Listings | 7,000 | 3,000 |
| Features | 61    | 61    |

Features span location (suburb, lat/long), property attributes (room type,
capacity, bedrooms/bathrooms), host attributes, and review metadata. Target:
nightly price (AUD). Preparing the raw fields involved parsing currency and
percentage strings to numerics, splitting the free-text `bathrooms` field
into a count plus shared/private flags, converting `host_since`,
`first_review` and `last_review` to age-in-days against a fixed reference
date, deriving amenity count and 16 amenity indicators, and grouping rare
categories before one-hot encoding.

## Approach

    inverse-transform.

1. Clean and impute missing values across the 61 raw features.
2. Engineer location, capacity and host-history features.
3. Transform the target with `log1p` to tame the right-skew shown above.
4. Benchmark five candidate models (Ridge, Elastic Net, Random Forest, Extra
   Trees, Histogram Gradient Boosting) on a 2,000-row subset.
5. Validate the top three on the full 80/20 split, then train the winner on
   all rows and confirm on the held-out competition test set.

## Results

Histogram Gradient Boosting won on every metric — roughly 12% better RMSE
and 14% better MAE than the Elastic Net baseline.

Excluding the top 1% of prices, the selected model recorded RMSE 96.90 and
MAE **A$50.20** — most of the error is concentrated in a small number of
ultra-premium outlier listings, not in the typical case a new host will hit.

<Insight title="The R² of 0.248 is honest, not disappointing" tone="warning">
  The price distribution is heavily right-skewed and a handful of extreme
  listings dominate squared error. That is exactly why the p99-excluded metrics
  (MAE 50.20) are reported beside the full-validation figures — a single average
  would hide what the model actually does well.
</Insight>

## Recommendation

<Insight title="For the business" tone="success">
  Use the model's predicted price as the **default starting price shown to a new
  host**, framed as a range of roughly ±A$50–70 rather than a single number.
  Because the model explains about a quarter of price variance (R² = 0.248),
  pair it with a short host-facing note that unique amenities or standout photos
  can justify pricing above the suggestion — the model is a floor for a
  data-driven conversation, not the final word.
</Insight>

## What I'd do next

- Add seasonality and local-event features — the current 61 features are
  static per-listing.
- Report a prediction interval, not just a point estimate, so hosts see the
  uncertainty.
- Investigate the high-price segment separately — a two-stage model (typical
  vs premium) may cut the outlier-driven error further.

### Explored: prediction intervals as the priority

<Insight title="Why this one first">
  Of the three follow-ups above, reporting a **90% prediction interval** (via
  quantile `HistGradientBoostingRegressor`, α = 0.05 and α = 0.95) is the most
  valuable next step and the cheapest to build — it reuses the existing feature
  set and turns the current single-number prediction into an honest range for
  the host. The seasonality features would need an external events calendar, and
  the two-stage premium/typical split adds a second model to maintain for an
  error that's already partly explained by the A$50.20-vs-A$72.89 gap between
  typical and top-1% listings. The method is worked through in
  [`notebooks/melbourne-rental-prediction.ipynb`](https://github.com/Bibententen/portfolio/blob/main/notebooks/melbourne-rental-prediction.ipynb)
  — no new interval width is quoted here, because producing one honestly
  requires re-running against the original competition data, which isn't shipped
  in this repository.
</Insight>
